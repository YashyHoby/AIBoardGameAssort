# オンラインボードゲームプラットフォーム 企画書

**企画名（仮）：Online Board Game Platform**  
**文書バージョン：0.2**  
**作成日：2026-08-25**

---

## 1. 企画概要

本企画では、スマートフォンとWebブラウザから、複数のボードゲームをオンラインで遊べるプラットフォームを開発する。

ユーザーは 1 つのアプリ／Webクライアントを利用して、ゲーム一覧から遊びたいゲームを選び、ルームに参加して対戦する。最初のMVPではオセロを実装し、その後、別のゲームを追加できる共通基盤を構築する。

本企画の中核は、単一のゲームを作ることではなく、**共通プラットフォーム上で複数のゲームを追加可能な基盤**を作ることにある。ゲームごとのロジック、UI、通信契約を共通化し、ゲーム追加の開発コストを下げる。

---

## 2. 背景

ボードゲームをオンラインで遊ぶサービスは、ゲームそのものの開発だけでなく、認証、待ち合わせ、ルーム管理、対戦状態の同期、再接続、勝敗判定、運用基盤などの共通開発が必要になる。

そのため、ゲームを1本ごとに独立アプリとして作ると、実際に遊べる状態に到達するまでのコストが高くなる。

一方で、AIを活用したゲーム生成やゲーム企画の自動化は進んでおり、ゲームアイデアそのものは増やしやすくなっている。しかし、生成したゲームをすぐに遊べるようにするためには、**再利用可能なゲーム基盤**が必要である。

そこで、まずはプラットフォーム基盤を作り、次にオセロを最初の検証対象として実装し、その後に他ゲームを追加可能な仕組みを整える。

---

## 3. 解決したい課題

### 3.1 プレイヤー側の課題

- ゲームごとに別アプリを探す必要がある
- 一緒に遊ぶ相手を探すのが難しい
- 既存のゲームだけが主流で、新しいゲームを試しにくい
- 端末が違っても同じ対戦をしたい

### 3.2 制作者側の課題

- ゲームロジック以外の共通機能の開発コストが高い
- 新しいゲームを小さく公開して試すのが難しい
- ルールの仕様とUI・通信・検証の境界が曖昧で開発が分断しやすい

### 3.3 プロジェクト側の課題

- ゲーム追加の仕組みが不明瞭だと、MVPの範囲が広がりやすい
- 1本のゲームで完結しないと、要件と設計が混在しやすい
- 個別ゲーム仕様とプラットフォーム仕様を混ぜてしまうと、実装が難しくなる

## 4. 設計思想

### 4.1 プラットフォームとゲームを分離する

本プロジェクトは、以下の2層を明確に分離する。

- プラットフォーム基盤
  - 認証
  - ルーム作成
  - 招待・参加
  - 対戦状態の同期
  - 再接続
  - Realtime通信
  - 共通UI・共通画面

- ゲーム固有モジュール
  - オセロの盤面状態
  - 合法手判定
  - 勝敗判定
  - 盤面の投影ルール
  - 1手のアクション形式

この分離により、プラットフォームの実装と、個別ゲームの実装が独立して進められる。

### 4.2 MVPはオセロから始める

最初のMVPでは、1つのゲームとしてオセロを実装する。これは以下の理由がある。

- ルールが明確で単純
- 合法手判定と終局判定が明確
- 2人対戦で試しやすい
- 共通基盤の検証に適している

その後、別のゲームを追加して、ゲームモジュールの抽象化が成立しているか確認する。

## 5. プラットフォームとゲームの責務分離

### 5.1 プラットフォーム基盤の責務

- ユーザー認証
- プロフィール管理
- ルーム作成・招待・参加
- 対戦セッション管理
- Realtime同期
- 接続・再接続処理
- ゲーム一覧と選択
- 共通UIレイアウト
- クライアント共通通信契約

### 5.2 ゲームモジュールの責務

- 盤面状態の表現
- 手の合法性判定
- 盤面更新
- 勝敗判定
- 乱数やタイミングの制御
- 役割別の投影情報
- UI表示用メタデータ

### 5.3 禁止事項

- ゲーム固有のルールをUIに直接埋め込まない
- ゲームモジュールがSupabaseやネイティブAPIに直接依存しない
- クライアントが勝敗・手番・状態保存を自分で決めない
- サーバーが検証せずにクライアントの入力を採用しない

## 9. 結論

本企画の本命は、単なるオンラインゲームアプリではなく、**ゲームを追加できるプラットフォーム基盤**を作ることにある。MVPとしてはオセロを最初のゲームとして作り、プラットフォームが本当に汎用性を持つかを検証する。

この方針により、将来のゲーム追加やAI利用を見据えた設計にしたうえで、最初の実装は小さく、明確に、確実に進めることができる。

## 11. 本企画の特徴・差別化

### 11.1 「ゲーム」ではなく「ゲーム群」を提供する

一般的なスマートフォンボードゲームでは、1アプリにつき1ゲーム、または少数の固定ゲームを提供するケースが多い。

本企画では、継続的にゲームそのものが追加されることをサービス価値とする。

### 11.2 プレイヤー募集までサービス内で完結する

ゲームを提供するだけではなく、プレイヤーを集める機能をプラットフォームに含める。

これにより、

> 「面白そうだが一緒に遊ぶ人がいない」

という問題を軽減する。

### 11.3 AIと相性のよいゲーム基盤

Game Definitionと共通Game Engineによってゲーム構造を標準化する。

この標準化自体が、AIによる実装・検証・量産を行いやすくする。

### 11.4 実験的なゲームを公開しやすい

個別アプリとして公開するほどではない小規模なゲームでも、プラットフォーム内の1タイトルとして提供できる。

そのため、従来であれば作品化されなかったようなゲームアイデアも試せる。

## 12. MVP

最初のMVPでは「ゲームを大量に作ること」ではなく、**この仕組みで複数ゲームを提供できることの検証**を目的とする。

### MVPで実装するもの

- Androidアプリ
- アカウント
- ゲーム一覧
- ゲーム詳細・ルール
- 募集掲示板
- 対戦ルーム
- 2〜4人オンライン対戦
- テキストチャット
- 通報・ブロック
- 2種類以上のゲーム
- 共通Game Engine
- Game Definition
- 管理者向け最低限の管理機能

### MVPで検証すること

1. 2〜4人でオンライン対戦を最後まで完了できるか
2. 募集からゲーム開始まで自然に利用できるか
3. 異なる2種類以上のゲームを同一基盤上で動かせるか
4. 既存のプラットフォーム機能を大きく変更せず3本目を追加できるか
5. AIエージェントを使ってゲーム追加作業を効率化できるか

## 13. 開発方針

### 13.1 想定技術

| 領域 | 技術 |
| --- | --- |
| モバイルアプリ | React Native / Expo / TypeScript |
| バックエンド | Supabase |
| リアルタイム通信 | Supabase Realtime |
| データベース | PostgreSQL |
| ゲーム基盤 | TypeScriptによる共通Game Engine |
| 管理画面 | Next.js |
| ソース管理 | GitHub |
| AI開発 | Codex |
| CI/CD | GitHub Actions / EAS |
| 自動テスト | Vitest / Playwright等 |

### 13.2 GitHubを中心とした開発

アプリ、ゲームエンジン、ゲーム定義、Supabase設定、DB Migration、テスト、ドキュメント等を原則として1つのGitHubリポジトリで管理する。

```text
                  GitHub
                     │
        ┌────────────┼────────────┐
        ↓            ↓            ↓
      Expo       Supabase      Games
        │            │            │
        └────────────┼────────────┘
                     ↓
                  Codex
```

GitHubをプロジェクトのSource of Truthとし、AIエージェントも同じリポジトリを参照して開発する。

## 16. 成功指標

MVPではユーザー数そのものよりも、まずプラットフォームとして成立しているかを評価する。

### プロダクト成立性

- 2〜4人でオンライン対戦を完了できる
- 募集からゲーム開始まで完結できる
- 複数ゲームを同一アプリで提供できる

### 開発効率

- 既存共通機能を変更せず新ゲームを追加できる
- 3本目以降の追加工数が減少する
- Codexがゲーム実装・テストを一定範囲で自律実行できる

### 公開後に確認する指標

- 新規ユーザー数
- 対戦開始率
- 対戦完了率
- 募集成立率
- 1ユーザーあたりのプレイゲーム種類数
- 継続率
- ゲーム別プレイ数
- 新ゲーム追加後の利用率

## 18. リスクと検討事項

| リスク・論点 | 内容 | 方針 |
| --- | --- | --- |
| ゲームの面白さ | AI生成だけでは面白さを保証できない | 人間によるプレイテストを必須とする |
| ゲームEngineの汎用化 | すべてのボードゲームを共通化すると複雑になる | MVPでは扱えるゲームジャンルを限定する |
| 同期・不正 | クライアント側だけで判定すると不正や状態不整合が起きる | サーバー側をゲーム状態の正とする |
| UGC | 募集・チャットで不適切投稿が発生する | 通報・ブロック・モデレーションを用意する |
| AIの誤実装 | Agentが誤ったコードを生成する可能性がある | 自動テスト + Preview + 人間承認 |
| ストアポリシー | 動的なゲーム追加方式がストアポリシーに抵触する可能性 | 外部コード配信を避け、データ駆動設計を基本とする |
| 運用コスト | 利用者増加によりDB・Realtime費用が増える | MVPで実測し、成長後に構成を見直す |
| 独自性 | 単なるミニゲーム集との差別化が弱くなる可能性 | 募集体験・継続追加・実験的ゲーム・AI制作基盤を特徴とする |

## 20. 本企画の到達イメージ

本企画が目指すのは、単に複数のボードゲームを収録したアプリではない。

**オンライン対戦に必要な共通機能をプラットフォーム化し、AIと人間が継続的に新しいゲームを生み出し、そのままユーザーへ届けられる環境**を構築することである。

```text
               AI / Creator
                    │
             新しいゲーム
                    ↓
             Game Definition
                    ↓
             Game Platform
                    ↓
      ┌─────────────┼─────────────┐
      ↓             ↓             ↓
   Player A      Player B      Player C
      └─────────────┬─────────────┘
                    ↓
                Online Play
```

最初のMVPでは、この将来像のうち、

> **「共通基盤上で複数のゲームをオンラインで遊び、プレイヤー募集まで完結できる」**

ことを成立させる。
