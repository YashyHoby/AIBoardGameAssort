# オンラインボードゲームプラットフォーム 企画書

**企画名（仮）：Online Board Game Platform**  
**文書バージョン：0.1**  
**作成日：2026-08-25**

---

## 1. 企画概要

本企画では、スマートフォンから複数種類のボードゲームをオンラインで遊べるプラットフォームを開発する。

ユーザーは1つのアプリをインストールするだけで、2〜4人向けの複数のボードゲームから遊びたいゲームを選択できる。また、アプリ内の募集掲示板を利用して一緒に遊ぶ相手を探し、離れた場所にいるユーザー同士でオンライン対戦できる。

本企画の特徴は、単一のボードゲームを提供するのではなく、**共通のゲーム基盤上に新しいゲームを継続的に追加できること**にある。

さらに、生成AI・Codex等のAIエージェントを活用し、ゲーム企画、ルール作成、実装、テスト、バランス検証までを効率化することで、少人数でも多数のゲームを継続的に開発・提供できる環境を構築する。

---

## 2. 背景

生成AIの発展により、アイデア出し、ルール案の作成、ゲームデータ生成、プログラム実装、テストコード生成など、ゲーム制作に必要な作業の多くを高速化できるようになっている。

一方で、ゲームごとに独立したスマートフォンアプリを開発する場合、以下のような共通機能を毎回実装する必要がある。

- ユーザー認証
- オンライン通信
- 対戦ルーム
- プレイヤー募集
- チャット
- データ保存
- 通報・ブロック
- ストア公開
- 運用・アップデート

この方法では、ゲームそのものを生成・実装する速度が向上しても、アプリとして提供するための周辺開発がボトルネックとなる。

そこで、これらを共通化したプラットフォームを先に構築し、**「新しいゲームを作ること」と「オンラインサービスを作ること」を分離する**。

## 3. 解決したい課題

### 3.1 プレイヤー側の課題

オンラインでボードゲームを遊びたい場合、ゲームごとに異なるアプリやサービスを利用する必要がある。

また、2〜4人向けゲームでは、ゲームそのものだけでなく「一緒に遊ぶ相手を集めること」が必要になる。

特に知名度の低いゲームや新作ゲームでは、既存の友人だけでは人数を揃えにくい。

### 3.2 制作者側の課題

小規模な制作者がオンライン対応のボードゲームを公開しようとすると、ゲームルール以外にも認証、通信、マッチング、サーバー、ストア対応等を実装する必要がある。

結果として、新しいゲームアイデアを試すための開発コストが高い。

### 3.3 AIゲーム制作における課題

生成AIによってゲーム案を大量に作れるようになっても、それぞれを個別のアプリとして実装・公開する方法では量産性に限界がある。

AIを活用したゲーム制作では、個別ゲームの生成能力だけでなく、**生成されたゲームをすぐに遊べる共通実行環境**が必要になる。

## 4. 企画コンセプト

> **「ひとつのアプリに、次々と新しいボードゲームが増えていく。」**

本サービスでは、オンライン対戦、募集、ユーザー管理等をプラットフォーム側で共通化し、その上に複数のボードゲームを搭載する。

ゲームごとにアプリをインストールする必要はなく、ユーザーはゲーム一覧から気になるゲームを選び、その場で募集・参加して遊ぶことができる。

運営側では、共通のゲームエンジンとゲーム定義の仕組みを用いることで、新しいゲームを短期間で追加する。

将来的には生成AIを用いることで、

**アイデア → ルール → 実装 → シミュレーション → テスト → 公開候補**

までを半自動化し、人間は企画選定・品質確認・最終承認に集中できる状態を目指す。

## 5. 想定ユーザー

### 5.1 メインターゲット

- スマートフォンで気軽にゲームを遊びたい人
- 2〜4人程度の小規模な対戦・協力ゲームが好きな人
- 短時間で遊べる新しいゲームを探している人
- 一緒に遊ぶ固定メンバーがいない人
- 有名タイトルだけでなく、新しいゲームを試すことが好きな人

### 5.2 将来的なターゲット

- インディーゲーム制作者
- ボードゲームデザイナー
- AIを利用してゲームを制作したいクリエイター
- 実験的なゲームを公開・テストしたい開発者

初期段階では一般プレイヤー向けサービスとして構築し、制作者向け機能は将来拡張とする。

## 6. 提供価値

### 6.1 プレイヤーへの価値

#### 1つのアプリで様々なゲームを遊べる

ゲームごとに新しいアプリを探してインストールする必要がない。

#### 知らないゲームと出会える

ゲーム一覧や新着ゲームから、これまで知らなかった小規模ゲームを気軽に試せる。

#### 一緒に遊ぶ人を探せる

アプリ内の募集掲示板から、一緒に遊ぶユーザーを探せる。

#### 離れた人とも遊べる

インターネットを通じて、場所を問わず2〜4人で遊べる。

### 6.2 運営・制作者への価値

#### 共通機能を再開発する必要がない

認証、募集、通信、ルーム、通報などをゲームごとに実装する必要がない。

#### 新しいゲームを小さく試せる

新作ゲームを短期間で追加し、ユーザーの反応を確認できる。

#### AIによるゲーム開発を活用しやすい

ゲームの形式を一定にすることで、AIエージェントによる生成・実装・テストを自動化しやすくなる。

## 7. 基本的な利用体験

想定する利用フローは以下とする。

```text
アプリを起動
    ↓
ゲーム一覧を見る
    ↓
気になるゲームを選ぶ
    ↓
ルール・人数・プレイ時間を確認
    ↓
「募集を探す」または「募集する」
    ↓
2〜4人がルームに集まる
    ↓
ゲーム開始
    ↓
オンライン対戦
    ↓
勝敗・結果表示
    ↓
別のゲームを探す
```

サービス内で、

**探す → 集まる → 遊ぶ → 次のゲームを探す**

までを完結させる。

## 8. 主要機能

### 8.1 ゲームを探す

- ゲーム一覧
- 新着ゲーム
- ゲーム詳細
- 対応人数表示
- 想定プレイ時間
- ルール説明
- 遊び方

将来的には評価、人気順、ジャンル、難易度等による検索・推薦も検討する。

### 8.2 プレイヤーを募集する

ユーザーはゲームを指定して募集を作成できる。

募集には以下の情報を設定する。

- 対象ゲーム
- 募集人数
- 開始予定時間
- コメント
- 初心者歓迎等の条件

他ユーザーは募集一覧から参加できる。

### 8.3 対戦ルーム

参加者が集まると、専用ルームでゲームを開始する。

ルームでは以下を扱う。

- 参加者一覧
- Ready状態
- チャット
- ゲーム開始
- 再接続

### 8.4 オンラインゲーム

2〜4人がインターネット越しに同じゲーム状態を共有する。

カード、駒、得点、ターン等の状態をサーバーで管理し、各ユーザーの操作を同期する。

### 8.5 安全に利用するための機能

- ユーザー通報
- 投稿通報
- ブロック
- 不適切投稿への対応
- アカウント削除

## 9. ゲーム追加の仕組み

本企画では、新しいゲームを追加するたびにアプリ全体を新規開発しない。

アプリ側に共通のゲーム機能をあらかじめ実装する。

例：

- カード
- 山札
- 手札
- ダイス
- 駒
- マス
- ターン
- 得点
- プレイヤー選択
- 公開情報
- 非公開情報
- 勝敗判定

各ゲームでは、それらをどのように利用するかを**Game Definition（ゲーム定義）**として記述する。

```text
ゲームA ─┐
ゲームB ─┼─→ Game Definition
ゲームC ─┘
                ↓
        共通 Game Engine
                ↓
          スマートフォン
```

これにより、新しいゲームを追加するときの作業範囲を小さくする。

## 10. AIを活用したゲーム開発

本企画では、AIを単なるプログラミング補助ではなく、ゲーム制作工程全体を効率化するエージェントとして利用する。

### 初期段階

```text
人間
 ↓
ゲームアイデア
 ↓
Codex
 ↓
実装
 ↓
テスト
 ↓
人間がプレイ
 ↓
修正
 ↓
公開
```

### 将来像

```text
テーマ・条件を入力
       ↓
ゲーム案生成
       ↓
ルール生成
       ↓
Game Definition生成
       ↓
Codexによる実装
       ↓
自動テスト
       ↓
AIプレイヤーによる大量シミュレーション
       ↓
バランス・不具合検出

自動修正
       ↓
```

ただし、本番環境への公開は完全自動化せず、人間による確認・承認を挟む。

## 11. 本企画の特徴・差別化

### 11.1 「ゲーム」ではなく「ゲーム群」を提供する

一般的なスマートフォンボードゲームでは、1アプリにつき1ゲーム、または少数の固定ゲームを提供するケースが多い。

本企画では、継続的にゲームそのものが追加されることをサービス価値とする。

### 11.2 プレイヤー募集までサービス内で完結する

ゲームを提供するだけではなく、プレイヤーを集める機能をプラットフォームに含める。

これにより、

> 「面白そうだが一緒に遊ぶ人がいない」

という問題を軽減する。

### 11.3 AIと相性のよいゲーム基盤

Game Definitionと共通Game Engineによってゲーム構造を標準化する。

この標準化自体が、AIによる実装・検証・量産を行いやすくする。

### 11.4 実験的なゲームを公開しやすい

個別アプリとして公開するほどではない小規模なゲームでも、プラットフォーム内の1タイトルとして提供できる。

そのため、従来であれば作品化されなかったようなゲームアイデアも試せる。

## 12. MVP

最初のMVPでは「ゲームを大量に作ること」ではなく、**この仕組みで複数ゲームを提供できることの検証**を目的とする。

### MVPで実装するもの

- Androidアプリ
- アカウント
- ゲーム一覧
- ゲーム詳細・ルール
- 募集掲示板
- 対戦ルーム
- 2〜4人オンライン対戦
- テキストチャット
- 通報・ブロック
- 2種類以上のゲーム
- 共通Game Engine
- Game Definition
- 管理者向け最低限の管理機能

### MVPで検証すること

1. 2〜4人でオンライン対戦を最後まで完了できるか
2. 募集からゲーム開始まで自然に利用できるか
3. 異なる2種類以上のゲームを同一基盤上で動かせるか
4. 既存のプラットフォーム機能を大きく変更せず3本目を追加できるか
5. AIエージェントを使ってゲーム追加作業を効率化できるか

## 13. 開発方針

### 13.1 想定技術

| 領域 | 技術 |
| --- | --- |
| モバイルアプリ | React Native / Expo / TypeScript |
| バックエンド | Supabase |
| リアルタイム通信 | Supabase Realtime |
| データベース | PostgreSQL |
| ゲーム基盤 | TypeScriptによる共通Game Engine |
| 管理画面 | Next.js |
| ソース管理 | GitHub |
| AI開発 | Codex |
| CI/CD | GitHub Actions / EAS |
| 自動テスト | Vitest / Playwright等 |

### 13.2 GitHubを中心とした開発

アプリ、ゲームエンジン、ゲーム定義、Supabase設定、DB Migration、テスト、ドキュメント等を原則として1つのGitHubリポジトリで管理する。

```text
                  GitHub
                     │
        ┌────────────┼────────────┐
        ↓            ↓            ↓
      Expo       Supabase      Games
        │            │            │
        └────────────┼────────────┘
                     ↓
                  Codex
```

GitHubをプロジェクトのSource of Truthとし、AIエージェントも同じリポジトリを参照して開発する。

## 14. 開発環境・AIエージェント運用

想定する開発環境は以下とする。

- VS Code：人間によるコード確認・編集
- ChatGPT / Codex：エージェントによる実装
- Codex CLI：テスト・タスク実行・自動化
- GitHub：コード、設計、変更履歴の管理
- Supabase CLI：DB・Functionのローカル管理
- EAS CLI：Expoアプリのビルド・配布

AIエージェントに本番環境を直接変更させるのではなく、

```text
Local
 ↓
Test
 ↓
GitHub
 ↓
Staging / Preview
 ↓
人間が確認
 ↓
Production
```

という流れを基本とする。

## 18. リスクと検討事項

| リスク・論点 | 内容 | 方針 |
| --- | --- | --- |
| ゲームの面白さ | AI生成だけでは面白さを保証できない | 人間によるプレイテストを必須とする |
| ゲームEngineの汎用化 | すべてのボードゲームを共通化すると複雑になる | MVPでは扱えるゲームジャンルを限定する |
| 同期・不正 | クライアント側だけで判定すると不正や状態不整合が起きる | サーバー側をゲーム状態の正とする |
| UGC | 募集・チャットで不適切投稿が発生する | 通報・ブロック・モデレーションを用意する |
| AIの誤実装 | Agentが誤ったコードを生成する可能性がある | 自動テスト + Preview + 人間承認 |
| ストアポリシー | 動的なゲーム追加方式がストアポリシーに抵触する可能性 | 外部コード配信を避け、データ駆動設計を基本とする |
| 運用コスト | 利用者増加によりDB・Realtime費用が増える | MVPで実測し、成長後に構成を見直す |
| 独自性 | 単なるミニゲーム集との差別化が弱くなる可能性 | 募集体験・継続追加・実験的ゲーム・AI制作基盤を特徴とする |

## 20. 本企画の到達イメージ

本企画が目指すのは、単に複数のボードゲームを収録したアプリではない。

**オンライン対戦に必要な共通機能をプラットフォーム化し、AIと人間が継続的に新しいゲームを生み出し、そのままユーザーへ届けられる環境**を構築することである。

```text
               AI / Creator
                    │
             新しいゲーム
                    ↓
             Game Definition
                    ↓
             Game Platform
                    ↓
      ┌─────────────┼─────────────┐
      ↓             ↓             ↓
   Player A      Player B      Player C
      └─────────────┬─────────────┘
                    ↓
                Online Play
```

最初のMVPでは、この将来像のうち、

> **「共通基盤上で複数のゲームをオンラインで遊び、プレイヤー募集まで完結できる」**

ことを成立させる。
